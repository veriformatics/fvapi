## Intent

fvapi is an API for formal verification. Someone who wants something formally verified can call it. When our private library can speed up the work, fvapi uses the library, and it still gives the caller everything that they need to prove the result true themselves. fvTrace and fva use fvapi, also for their own normal work. Future applications can use it too, including applications that other people write.

fvapi runs on `vflab`, a machine dedicated to it. vflab does the actual work, stores the artifacts and holds the library. While few requests arrive, vflab keeps working on its library and improves it. The Claude sessions that control fvapi run on the founder's desktop, and the fvapi repository lives there. The sessions use vflab for the work, for the storage of artifacts and for the upkeep of the machine.

## Decisions

- Name + scope (user rulings): `fvapi` = the hosted multi-user service that fvTrace's `Decisions` reserve ("separate paid product, other repo"): library endpoints first; compute endpoints (fvTrace's exact plan search past its local limit, verifier replays, large what-if sweeps) later, on rented hardware. fvTrace + fva gain the capability to call it, also for their own normal work.
- Openness (user ruling): everything that does not conflict with the moat is public (free GitHub CI); the library content stays private.
- Host (user rulings): vflab serves fvapi alone, never as an offload host (not even for formal-verification work). Ubuntu 26.04 LTS; plain root (LVM, ext4) on the SATA SSD (no TPM on the board; encryption low priority); the two NVMe drives = ZFS mirror `data` at `/srv/data` with native encryption (key on root, backup on the controller). Static 192.168.40.241 + DHCP; admin login `eturkes@` by key alone (user ruling: renamed from the installer's `offload`, a name that implied an offload-pool host).
- Sessions + placement (user rulings): Claude sessions + this repository live on the desktop; vflab does all the work — the service, the store, and fvapi's own builds, gates + spikes (in a low-priority slice that yields to the service) — and is maintained from there; the public GitHub CI stays (`Openness`).
- Request-time answers use no LLM (subscription terms: Claude Code "Customers may not pay for, resell, or intermediate Claude usage on their end users' behalf"; OpenAI's sign-in terms prohibit "Using one user's subscription to fulfill another user's requests") ⇒ lookups, proved checkers, CPU automation; LLM work = the library's own development, or paid API keys later.
- Prototype set (user rulings): v0 HTTP+JSON API on vflab + a browser console (catalog, request playground, bundle view, demand log) + `fvapi` CLI client that fetches a bundle and replays it; Python FastAPI via uv; runs + is inspected on vflab alone; real replay for one entry (`vf.contrast-2x2`, a factorial contrast checker importing `Std` alone), the fva seeds = recorded stubs labelled as such; console = full variant fan-out (≥10 conventional + ≥5 unconventional).
- Library content stays out of git (repo `veriformatics/fvapi` = public): code + formats are committed; entries, proofs, seed metadata + study details reach vflab's store through `seed.py` from local sources alone (seed manifest `prototype/fvapi/seed.local.json`, gitignored); fixtures + examples in git = synthetic, or drawn from public fva (Apache-2.0).
- Console direction (user ruling, from 16 variants): combine `u02-instrument-panel` × `v10-dependency-graph`. Keep from u02: verdict readout (a tad smaller than u02's), entry selector + editable input tray, chart-recorder log of answers + demand. Keep from v10: proof graph (entry → artifact → closure files → requirements + toolchain), lookup lighting the matched path + check lighting the checker node, demand misses as dangling nodes. Not kept: u02's enamel instrument material, v10's graph↔list toggle (an accessible text alternative stays, per the UI quality floor). Explored as 5 combinations; user picked `c1-panel-scope` (panel-led: selector, input tray + compact verdict readout, proof graph in an inset scope, recorder strip below).
- Lookup (user rulings): every supplied key (`spec_id`, `artifact_sha256`, `statement`) must point to the same entry; any disagreement = a miss logged as demand, naming the mismatch (a proof about another build never answers). Several matching entries → one, by a published ranking (newest revision, then widest coverage), plus metadata naming every other match (count + entry and revision ids).
- Delivered-bundle terms (user ruling): decided later; until then every private-library bundle states "provisional: internal evaluation only", and final terms are set before any outside caller receives a bundle.
- Re-check trust (user ruling): the API stays one request → answer + bundle; the optional re-check runs caller-side in the open-source client against a client-held axiom allowlist (default `propext`, `Classical.choice`, `Quot.sound`, caller-editable); the bundle's own axiom list is displayed, never trusted; plus an optional container for a re-check independent of the caller's Lean install, built locally from the committed Containerfile; public-registry publication: not yet (user ruling).
- Library work (user rulings): no proving automation this phase. New-proof requests + lookup misses become queued rows (queued → being proved → added, shown in the console), kept in a gitignored file in this repo mirrored from vflab's queue (the repo is public). The founder proves rows in Claude sessions from time to time: library development that picks its own targets, never fulfilling a specific outside caller's request (subscription terms). Admission = the `Answer guarantee` kernel policy alone, no statement review gate. Intent's idle-work sentence waits for automation (`.agent/deferred.md`).
- IMPLEMENT scope (user rulings): the service ships library lookups, existing checkers + new-proof requests as queued rows (`Library work`). One founder account (one key, one history) = this phase's only caller. Acceptance = the founder through the API, the CLI + the MCP adapter, plus contract tests that run fva's flow (lookup → fetch → `fva trust`) and fvTrace's flow (lookup → fetch → re-check → receipt) against the live service; fva + fvTrace adopt the client in their own sessions. Third-party onboarding (identity, per-application keys, limits, payment, ZDR, isolation, final terms) later.
- Request data (user rulings): requests feed library building by default; the only opt-out = paid zero data retention (ZDR: no request content or result stored after the response; kept: caller id, time, route, status), which also removes the caller from library learning; a caller never sees another caller's requests, answers or demand. ZDR + per-caller isolation ship with third-party onboarding; every stored record carries a caller id. Operator blindness (goal: a proof that the operator cannot read sensitive request content while the library still learns) = research only this phase: a design + proof plan in `docs/`, the mechanism later. Prototype's global demand + answer logs = placeholder.
- Self-verification (user rulings): fvapi itself is formally verified. Trust test: a component stays trusted only where users of a formal-verification service would reasonably accept it (e.g. the Lean compiler + runtime, the OS); whatever they would expect verified is verified, by us or upstream (e.g. Lean's verified kernels con-leche + con-ron, HACL* hashing).
- Stack (user ruling): Lean 4 throughout (toolchain 4.35.0 now) — server, client, Lean caller library, MCP adapter + proofs in one Lake package; library entries are Lean.
- Answer guarantee (user ruling): exact theorem, labelled. A theorem answer is checked caller-side against the caller's own statement + axiom list: Lean's default kernel + ≥1 kernel of another implementation accept, none rejects, crashes or times out (a kernel may decline only for a named unsupported feature), and the answer names the accepting kernels (incl. con-leche + con-ron). A checker answer carries a kernel certificate over the caller's exact input bytes; past the time budget its verdict is labelled `compiled evaluation (trusts the Lean compiler)`. Artifacts are named by their exact bytes; a partial answer is labelled partial, never a full success.
- Audience + surfaces (user rulings): programs + agents first — the API, the CLI, the Lean caller library + a small stdio MCP adapter over the same API (this phase) = the product; the console = the founder's inspection surface.
- Code licence (user ruling): Apache-2.0 (`LICENSE`, canonical text); library content stays private and unlicensed.
