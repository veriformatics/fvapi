## P1 Kernel policy (`Fvapi/Verify/Policy.lean`, shipped, Std-only)

- `KernelId` = closed set `leanchecker` (Lean's default), `leanchecker-paranoid`, `lean4lean`, `nanoda`, `con-leche`, `con-ron`; lineage derived from the id, never from result text or a profile field: `lean` = the first three (modes of one kernel + a port derived from it: lean4lean's README calls itself "not really an independent implementation"), `nanoda`, `con` = the last two. "A kernel of another implementation" (`Answer guarantee`) = lineage ≠ `lean`.
- Statuses: `accept`, `reject`, `decline (feature)`, `crash`, `timeout`. Layout (keeps U1's `Fvapi/**` = shipped): reviewed vocabulary `FvapiSpec/<Domain>.lean`, closed claims `FvapiSelf/<Domain>.lean`, proofs `FvapiProof/<Domain>.lean`, aggregate proof root `FvapiProofs.lean` (its own Lake library). Reviewed spec `FvapiSpec/Policy.lean`: `Pass rs` := leanchecker reported `accept` ∧ some kernel of lineage ≠ `lean` reported `accept` ∧ no result is `reject`, `crash` or `timeout` ∧ every `decline` names a nonblank feature, where blank = empty after removing leading + trailing space, tab, LF and CR (Lean 4.35 `String.trimAscii`; vertical tab, form feed, NBSP and other Unicode spaces count as content). Closed claim `FvapiSelf/Policy.lean` `PolicyExact := ∀ rs, verdict rs = .pass ↔ FvapiSpec.Policy.Pass rs`; proof `FvapiProof/Policy.lean`. `verdict` judges validated facts; run-set completeness is P3's (exactly one result per profile kernel, no duplicate or extra id; a missing run or tool = failure, never an implicit decline).
- A decline comes only from a kernel's pinned unsupported-feature mapping (P2 `status_map`); a generic nonzero exit, an absent feature, a timeout, an OOM or a budget exhaustion never supplies one.
- Controls (theorems + tests): leanchecker accept + the five others validly declining → fail (no independent acceptance; every other premise holds); the three `lean`-lineage kernels accept + the other three validly decline → fail; leanchecker accept + nanoda accept → pass; leanchecker missing → fail; any reject / crash / timeout → fail; empty list → fail; blank or whitespace-only feature → fail. `accepting profileOrder rs` returns exactly the accepting ids, once each, in profile order, never a declined one (own proof obligation).

## P2 Verification profile (`verify/profile.json`, schema 1)

- Fields (ruling on A8): `version` 1; `id` = `"sha256:"` + sha256 of the UTF-8 bytes of `jq -S -c 'del(.id)'` over the profile, without the trailing newline (a golden byte + digest fixture fixes the rule; U3 keeps these bytes or introduces a versioned transition); `toolchain`; `runtime` = the toolchain artifact identity (verified distribution manifest: Lean, Lake, runtime libraries, by hash); `export_format` `"fvapi.export.v1"`; `exporter` `{executable, sha256}`; `comparator` `{executable (lake), sha256, source "Lake/CLI/Check.lean", source_sha256, targets[]}` (targets = the comparator's primitive targets + permitted-axiom declarations + conditional builtins for the axiom allowlist, compared as a set against the installed source); `kernels[]` `{name ∈ KernelId, executable, sha256, args[], config_template?, timeout_ms, status_map}` where `status_map` (ruling on A9: no JSON runner protocol) maps exit codes to `accept` | `reject` | `decline`, `decline_pattern` = a regex on stderr whose first group names the feature, an expired deadline → `timeout`, a signal / OOM / unmapped exit / malformed outcome → `crash`; `canaries` `{source_repo, source_commit, set_sha256, known_sha256, files{name: sha256}}`; `policy_version`; `caps` `{export_ms, comparator_ms, memory_bytes}` (candidates to measure, not capacity claims; a kernel's deadline is its own `timeout_ms` alone).
- Run set: fvapi's own profile names all six kernels; a caller-held profile (`verify --profile FILE`, `FVAPI_PROFILE`, also `fetch_and_verify`, `check --verify`) names a nonempty set containing leanchecker + ≥ 1 kernel of lineage ≠ `lean`. The policy is fixed in the client, never read from a profile; a bundle never chooses the profile. A profile with no canaries is a synthetic test profile and claims no compatibility assurance.
- Gate stage `profile`: schema, run-set rule, executed-artifact identities (each executable, the exporter, Lake + comparator, runtime manifest, generated kernel configurations) and actual canary bytes match; diagnostics name the differing field; missing data fails.
- Compatibility corpus `verify/compat/` (nonempty: a valid positive claim + known-false controls, pinned challenge + solution exports, expected comparator result, expected per-kernel statuses + features, final verdict) replays on every gate run (or through an exact profile + corpus + runner content-keyed cache); every known-false control fails the complete acceptance path. A change to expected results or cases follows the approved grading-change rule (CLAUDE.md `Engineering`).

## P3 Per-claim replay (`fvapi dev replay`, Lean in the `Fvapi` library, reused by U9)

- Input: validated nonempty inventory (P4), validated profile, an explicit trusted expected-source snapshot and the axiom allowlist (U2: `propext`, `Classical.choice`, `Quot.sound`; the interface takes a caller-held allowlist + expected snapshot independently of any solution or bundle). The snapshot names the reviewed claim declaration and its transitive statement + implementation closure by bytes; it is materialized + hashed before the solution is built or mutated, in a separate build tree verified unchanged; refreshing it is a reviewed input change, never a response to a mismatch.
- Challenge root = that snapshot + fresh theorem stubs: per inventory proof, the same fully qualified theorem name, type exactly its claim constant, body `by sorry` (proof implementations neither copied nor imported; statement definitions kept, not sorried; `definition_names` empty; challenge-only sorry warnings allowed locally).
- Each side builds + exports from its own root: `leanexport` with the proof constant + the profile targets (full closure); comparator gets exactly those two files (`--challenge-from-export`, `--solution-from-export`), a one-theorem config and the allowlist; comparator's aggregate paranoid mode stays off (profile kernels run separately); its own default-kernel run is bounded and costed. Then every profile kernel runs alone on the immutable solution export through its `status_map` adapter, with finite export / comparator / kernel deadlines, the enclosing memory + process caps, and the owned process tree reaped on failure; deadline expiry (recorded by the runner) = `timeout`, any other signal or OOM = `crash`.
- Claim PASS ⟺ profile + inventory + snapshot validation ∧ both complete exports ∧ comparator rc 0 ∧ complete unique coverage of the profile's kernels ∧ P1 `verdict` = pass. One JSON record per claim: snapshot, profile + config identities, export sha256s, comparator status + rc, per kernel `{name, lineage, status, feature?, wall_ms, rc}`, `causes[]`, verdict. Cause codes (ruling on A9): `challenge_mismatch`, `forbidden_axiom`, `kernel_missing`, `kernel_rejected`, `kernel_crashed`, `kernel_timeout`, `unnamed_unsupported`, `insufficient_independent_kernels`, `profile_mismatch`, `kernel_identity_mismatch`, `export_failed`, `comparator_error` (setup, parse or kernel failure inside comparator, apart from a statement mismatch) (+ `input_mismatch` for certificate replay, U10). Command rc 0 ⟺ ≥ 1 claim and exactly all expected claims pass. Never whole-package `lake check --paranoid`.

## P4 Claim inventory (`verify/claims.json`) + obligation matrix (`docs/obligations.md`)

- Entry: id, domain, helper-spec module (`FvapiSpec.<Domain>`), closed-claim module (`FvapiSelf.<Domain>`), claim name, proof theorem + module, aggregate proof root (`FvapiProofs`, a declared buildable Lake target importing every proof), exact audit subject modules, reviewed-surface budget, expected-snapshot identity, shipped call paths.
- Gate stage `inventory` reads elaborated declaration metadata (not a source regex): every Prop-valued definition in a closed-claim module (inferred or aliased Prop types included) is closed, universe-free and has exactly one row; ids + names unique; each proof is a theorem whose type is exactly the named claim constant; helpers live in Spec modules; no closed-claim module imports another domain's Self or Proof module (transitive closure); every audit root, subject and call path resolves to its intended declaration kind; every call path lies in the production import surface.
- Production roots (`Fvapi`, `Main`) vs audit roots (`FvapiProofs`) are declared; the production import closure excludes `FvapiSpec`, `FvapiSelf`, `FvapiProof`, `FvapiProofs` and audit-only modules; `Fvapi/**` stays exactly the shipped set (stage `imports` extended: no `Fvapi/**` module imports a sibling audit tree; probe).
- `docs/obligations.md`: promise id → inventory claim → implementation + shipped call paths → proof | test → coverage status → residual trust; checked both ways against the inventory; semantic adequacy = an explicit review ruling, pending obligations stay visibly pending.

## P5 Verifier capsule (`tools/build-capsule.sh`, `verify/capsule.lock`)

- The lock pins one public immutable fva commit + the toolchain, runtime and dependency-manifest identities used to build it. fva + fvamut build from a fresh detached clean checkout, Mathlib through its pinned manifest + cache, pinned canary bytes fetched without repinning; `capsule.json` records pre/post cleanliness, dependency revisions, toolchain + runtime identity, retained runner-source identity, binary hashes.
- Acquisition is locked and published atomically after validation; the cache key covers lock, runtime, manifest, platform; every cache hit is revalidated before use (a partial, changed or mismatched capsule is rebuilt or fails closed). The capsule keeps fva's `.lake/build/bin/{fva,fvamut}` layout, manifests, runner sources, canary files and a separate writable area; the root is configurable (vflab default `~/gate/capsules/`, a keyed cache in CI). Executables run by absolute path under fvapi's `lake env`, whose sysroot exporter + kernels must match P2. The active fva checkout is never used. Cold + warm acquisition, retained disk and peak resources are measured.

## P6 Self-audit (gate stage `self-audit`)

- Per domain: `<capsule fva> trust <fvapi> --spec-module FvapiSelf.<Domain> --root-module FvapiProofs --subject <module>… --paranoid --budget <inventory budget> --canary-set <pinned> --known <pinned> --json` (explicit kernel + canary limit flags equal to the largest profile kernel `timeout_ms`), under a finite whole-invocation timeout + aggregate caps. Requires rc 0, a valid JSON envelope with `verdict = "pass"`, and a report whose claim / proof / subject identities equal the inventory and whose canary identities equal the profile; build or setup failure, malformed envelope, wrong claim set, timeout, crash or non-PASS fails, stderr + normalized cause kept. fva's module-level replay is an additional self-audit, never a substitute for P3.
- Scope = fvapi's own controlled source; fva's open gaps (D8 native-subject elaboration, D12 unsandboxed builds, D48/D49 unpinned oleans) bound what a PASS means; a delivered package earns the `Answer guarantee` through P3's caller-side path alone. Probes: planted `sorry`, custom axiom, recursive `partial` reached by a claim → FAIL with tags `axiom` / `axiom` / `override`; malformed success output → FAIL.

## P7 Mutation (`verify/mutation/{config.json,results.tsv,rulings.tsv}`)

- Graph roots: `Fvapi`, `FvapiSpec`, `FvapiSelf`, `FvapiProof`, `Fvapi.lean`, `FvapiProofs.lean`, `Main.lean`, `Tests.lean` (+ later dev roots); exeRoots `Main`, `Tests`; proofRoots `FvapiProofs`; exes = the Lake targets; target groups = the production files the credited tests import or call (default operators); keyFiles include `lakefile.lean`, `lean-toolchain`, profile + capsule identities; exclusions + zero-site declarations enumerated and ruled.
- Stage `mutation-scope`: command-level def / abbrev / instance coverage checked against an independent declaration inventory; a wrapped `<command> in` definition fails.
- Stage `mutation` = `lake env <capsule fvamut> check --config verify/mutation/config.json` from the fvapi root under a fvapi-owned mutation lock (shared with update): no selection; `min(3, mutants)` distinct seeded rows replayed; every expected row current for its runner / config / tool / stage / input identities; every survived or inconclusive row has an independent current ruling (`equivalent` | `unspecified` reasoned against the contract; `resource` for inconclusive only, no kill credit) linked to its review-ledger decision; tracked bytes unchanged. `tools/mutation-update.sh` (capped, same lock) runs complete campaigns; OOM, timeout, setup failure, incomplete runs and unviable mutants earn no credit.
- Test adapters keep the existing failure-count outputs but expose fvamut's protocol: 0 pass, 1 assertion failure(s), 2 setup, 3 crash (planted 1-, 2-, 3-assertion failures, a setup failure and a signal crash prove the mapping). Proof kills and executed test kills are separate evidence: crediting an already-passing test needs a fresh ad-hoc default-operator run with only its build stages + that test stage. U1's CLI mutation row closes once that covers `Fvapi/Cli.lean` through `Tests.lean` and the smoke path.

## Acceptance evidence

- The predicate + probe matrix is frozen before implementation: each new check has a clean control, a planted violation firing its own diagnostic, and byte-identical restoration; registered in the public gate (probes stage) and recorded in `.claude/rules/checks.md`. Matrix: policy controls + completeness + reporting; profile schema / artifact / config / target / canary tampering + compatibility controls; inventory (missing, duplicate, inferred-Prop, wrong proof type, unresolved or non-production call path, forbidden transitive import, missing matrix reference); challenge freeze + valid weakened-statement and dependency substitution + sorry + custom axiom + comparator failure despite kernel acceptance (each reaching comparator: the scratch fixture emits the export first); kernel reject / timeout / crash / malformed / unsupported-feature (fake kernels via a validated fixture profile, asserting the fake actually ran); capsule cold / warm + missing / partial / tampered tool, source or canary; self-audit claim set + tags + malformed output; mutation scope, stale identities, rulings, seeded-replay mismatch, adapter classification, tracked-table immutability.
- `fvapi dev replay` runs for real on a valid claim + representative comparator and kernel failures (JSON records + exit status asserted). Full + fast gate stage coverage, CI shard coverage, named not-run checks, and cold / warm / resource costs are recorded; a dominant stage gets an equal-strength speedup row.

## Boundary

- U2 proves the inventoried pure policy + reporting claims and runs the artifact, replay, self-audit and mutation checks on fvapi's controlled source; each proof states its fact boundary. The obligation matrix names result collection + status parsing, export + challenge binding, profile identity, inventory coverage and credit aggregation as obligations (pure decision parts proven, IO / compiler / runtime / tool boundaries tested + residual) — never implied by `PolicyExact` or an fva PASS.
- Profile, inventory, replay, capsule + self-audit, mutation-scope and mutation stages + probes register in `tools/gate.sh` + its CI shards with every prerequisite available on a clean shard (missing = incomplete, never green); fast-gate selection, timings, the dependency table and public pin automation (capsule lock, runtime, canaries) update with them. The public gate acquires the capsule from public pins and needs no desktop, vflab or private input: the capsule stages (`self-audit`, `mutation-scope`, `mutation`) form a third CI shard `audit` whose job restores the capsule from `actions/cache` keyed on `verify/capsule.lock` + runtime + platform (cold build on a miss), `fanout` covers it, and `docs/dependencies.md` gains rows for the fva capsule + its Mathlib cache source.
- U2 does not establish a delivered-bundle `Answer guarantee`, full product coverage, hostile-package safety, compiled-runtime refinement or proof-request automation; U8 / U9 / U12 reuse the policy + replay interface with caller-owned challenge, axioms and exact bundle + input identities.
